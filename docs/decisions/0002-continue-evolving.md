# ADR 0002 — 继续演进 ptc-roles（附证据窗口与退役条件）

- 日期：2026-09-15
- 状态：**已采纳**（2026-09-16 用户确认；决策规则与证据窗口照此执行，机制实现细节仍归
  `docs/dsh-v0.1.6-ptc-impact.md`）
- 前置阅读：`docs/dsh-v0.1.6-ptc-impact.md` —— **版本事实与 rc 后修复清单（P0–P3）的唯一来源**，本文不重复；
  本文只在「决策需要的粒度」上引用其结论。

## 背景

0.1.6 推翻了本 preset 立项的第一理由（ADR 0001「决定性证据」表第一行：PTC 下「只读角色」不成立），
于是「还有没有必要继续开发」成为一个真问题，而不是情绪问题。

## 决定性证据：当前实际状态（2026-09-15 实测）

`node scripts/verify-ptc-roles.cjs`（零模型成本，读**真实发往模型的工具面**）：

| 观测 | 值 |
|---|---|
| 本工作区会话 / 实际派出角色子代理 | 11 / 7 |
| 五个角色覆盖率 | **5/5**（explorer×2，librarian / oracle / implementer / designer 各 ≥1） |
| 角色白名单断言 | ✓8 ✗0 !0；每个角色精确匹配，仅「已知自身层泄漏」 |
| 角色子代理沙箱提权 | **0 次**（与 `approval/policy = never` 一致 —— ADR 0001 的 sandbox-strip 结论复现） |
| 意图门合规率 | 75%（9/12 会改变行为的轮次）—— **但双峰**：一场 9/10（90%），另一场 **0/2（0%）** |
| 主 agent 会话数 | 2，共 17 轮，且**都在 preset 自身仓库** |

**读法：验证充分、使用不足。** 其中两个数字是真问题：

1. 旗舰行为机制（意图门）可以**整场静默失效**；本部署 `logger.warn` 无落盘通道（`pitfalls.md` #9）
   ⇒ 「静默」是字面意义。
2. 存活窗口内**没有「非自身仓库的真实任务」使用记录** —— 会话库是滚动窗口（`pitfalls.md` #15），
   更早的记录不可考，故这是「未证」而非「证否」。

## 决策

**继续演进**：保留并深化 ①硬能力边界 ②每角色模型档；**停止扩张**，并主动收缩（净删机制）。
同时设**证据窗口 + 退役条件**（见「后果」）。

## 为什么不是「退役」：三条价值腿逐条复核

| 价值腿 | 上游是否提供 | 0.1.6 后状况 | 判定 |
|---|---|---|---|
| ① 硬能力边界（`toolFilter.allow` 按角色裁剪） | ❌ 上游只有通用 `subagent`，无按角色裁剪 | 仅**安全论证**的那一半失效，机制本身仍独有 | **存活** —— 但 README「真正的能力边界」措辞失真：每个角色实测泄漏 `subagent` + `list_subagent_models` |
| ② 每角色模型档（成本分层） | ❌ 无 | 不受影响 | **最强的一条** —— 直接对齐本用户用 DSH 的主线目的（前缀缓存/成本优化）；但目前只是「猜的档位」，**无归因测量** |
| ③ 行为纪律（意图门 persona） | ❌ 无 | 不受影响 | **存疑** —— 单场可 0% 合规且失败不可见 |
| ④「PTC 下只读角色不可行」（原立项理由） | — | **被推翻**（read-only 策略下成立） | **已死** —— 但它逼出了整套验证基建，不是纯沉没成本 |

**结论：立项的第一理由死了，但它从来不是唯一理由。**

## 为什么值得继续：0.1.6 提供了「净删机制」的窗口

罕见地，这次升级让**自建机制可以被框架原语替换**：

| 现有自建机制 | 0.1.6 框架原语 | 净效果 |
|---|---|---|
| 4 层深度判据 + 手工复刻 `depth.ts` 公式 | `sandbox/mode` 每 session 策略 + 委派自动 seed | 边界从「插件判据正确性」迁到「框架策略强制」 |
| 「翻转失败 = 安全事件」 | read-only 策略使漏判降级为**功能**事件 | 失败后果减一档 |
| `agent/created` 翻转时序风险 | 框架改为异步串行 + 首个模型请求等待其完成 | 时序保证白送 |

若这几件做完，**代码量应下降而安全性上升** —— 方向收敛而非发散，这是「值得继续」的主要依据。

## 被否决的替代方案

- **直接退役**：会丢掉 ①②，而 ② 恰是本用户用 DSH 的主线目标（成本）。且当前证据不足以判定它「无效」——
  只有「未证」。**否决**，但保留退役条件（见「后果」）。
- **原样继续扩张**（加角色 / 加机制 / 加面板）：验证基建体量已接近甚至超过交付物
  （`pitfalls.md` 157 行 + 3 个 verify 脚本 + 6 份 evidence + 474 行 yml + 2 个 mjs + 6 份 persona），
  而真实任务使用记录为零；对抗的又是 issue 已关闭、无法上游、快速迭代的上游。**否决**。
- **收敛为 workflow 原语**（角色的未来形态改由 `workflowEngine` 承载）：`dsh-deep-research` 已占该路线，
  两条编排线并行会让维护成本翻倍；且 preset 的 child-scoped persona 与 `toolFilter` 是 workflow **给不了的**。
  **本轮否决**，列为长期收敛方向（见「待决」2）。
- **全 native preset**：主 agent 每轮吃全量工具 schema（157 个），与成本定位冲突 —— ADR 0001 已否决，结论不变。
- **全 PTC 角色**：ADR 0001 已否决；0.1.6 后**机制上重新可行**，但需先答「只读角色是否要求读范围受限」，
  见「待决」3。

|---|---|

| 不测 | 视为「没必要」：它会继续以当前比值消耗，而无法判断是否在帮忙 |


**窗口读数（2026-09-20 小结 · 8 场真实任务）** —— 两个规模的配对对照各一次，结论一致：

| 配对 | 产出 | 成本倍数 | 用户判定 |
|---|---|---|---|
| v1 ignorecheck（小） | 等价（13/13；我的越界探查 17/20 对 17/20，且**差异条目完全相同**） | **6.4×** | 有角色「好用」· 无角色「好」 |
| v2 miniql（大 1.5×） | 等价（17/17；越界探查 **18/18 对 18/18**） | **2.4×** | 有角色「中性」· 无角色「**好用**」 |

- **产出改善：至今为零。** 两次配对、两种规模，角色臂都没有做到无角色臂做不到的事（越界探查由编排器独立编写，数据用 Python `csv` **独立装载**）。
- **成本倍数不收敛（v3 否证了早先的乐观读法）**：6.4×（v1）→ 2.4×（v2）→ **3.6×（v3）**，在 ~4× 附近波动；按行算 14.1k → 4.1k → 13.1k token/行（对侧 3.5k / 2.3k / 6.3k）。
- **用户判定的落点始终在过程面**：三次高判定的理由是「能正确派遣 librarian」「能正确识别需求」「完成速度快、效果一样」—— **没有一次是「产物更好」**。
- **价值出现的形状（当前假设）**：**体量型外部/本地取证** → 角色真去干活（第六场 好用）；**内聚实现** → 机械化派发（v2：7 个所有权行 → 7 个同型子代理，且这份切分本身制造了额外协调成本 —— 跨行值模型与协议必须另行冻结）。
- **未排除**：更大赛度是否继续收敛 —— **v3 已答：不收敛**（见下）。
- **质量面（v3 已答）**：角色臂多写 2.1–3.3× 测试的长期可靠性，用两轮固定种子探针（共 2400 条）比过，**两臂零差异**（见下）。

**窗口读数（2026-09-21 更新 · 第 8–10 场：v3 urlnorm 两臂 + 两轮质量探针）**

| 配对 | 产出 | 成本倍数 | 墙钟 |
|---|---|---|---|
| v1 ignorecheck（小） | 等价（13/13；越界 17/20 对 17/20，差异条目相同） | 6.4× | ~2× |
| v2 miniql（中） | 等价（17/17；越界 **18/18 对 18/18**） | 2.4× | ~2.8× |
| v3 urlnorm（大） | 等价（39 条清单都过；越界 **26/26 对 26/26**；迁移报告都 20 条差异） | **3.6×** | ~4.6× |

**两轮质量探针（固定种子，共 2400 条）**
- 400 条随机（含 12% 畸形）：两臂都 **400/400**；
- 2000 条对抗（15% 非法 · 10% 多斜杠/反斜杠/空端口 · 10% 注入制表符或换行 · `%2e`/字面 `%`）：两臂都 **1999/2000**，**且失败的是同一条**
  （`fIle://localhost/a:b/./../a:b` —— file URL 的 Windows drive letter 规则，**两臂共有的真 bug**）。
⇒ **零处「一臂对、另一臂错」**：多写测试换不到可测的可靠性；也说明**冻结清单本身有盲区**（下一版契约该把这类加进清单）。

**机制：为什么角色买不到产出、却更贵更慢**
1. **主-子不共享前缀缓存**：第 1 步主 agent 即命中缓存 **31,488** token，而子代理只命中 ~3,900 ⇒ 委派 = **把公共上下文按子代理数量再付一遍**
   （v3 未缓存输入 **6.7×**：435,793 vs 64,823）。
2. **并行是真的，但总工作量翻了 5.5×**：7 个子代理时长之和 **114 分钟**、并集只有 **39.2 分钟**（串行度 34%）⇒ 并行确实省了墙钟；
   但模型调用 **275 vs 50**，且临界路径 = 最慢子代理（39 分钟）+ 父级串行尾巴 ⇒ 仍慢 4.6×。

**判据：多角色划算的形状**（供后续任务决定是否派发）—— 必须**同时**满足：
1. **每块说明小而自足**（子代理只需父级上下文的一小部分）—— 缓存不共享，把全文契约喂给每个子块是最坏的复用形状（三场都犯了）；
2. **接口/约定由父级在派发前冻结一次**（子块之间不来回协商）—— v2 的 v2.1 值模型、v3 的 `AST.md` 都是切分自造的额外成本；
3. **每块显著大于协调开销、且父级几乎没有串行尾巴** —— 并行省下 114→39 分钟，但最慢子代理与父级尾巴决定了地板；
4. **本地没有可执行裁判** —— 否则单 agent 直接对着裁判迭代更快更省。
⇒ 三场真实任务里 ①④ 全违反、② 半满足、③ 不满足 ⇒ **这个窗口测的是「在单上下文可完成、且有本地裁判的任务上派角色」，答案是不值得**；
它**没有**测到「角色存在的理由」所在的形状（上下文装不下 / 无本地裁判 / 需墙钟并行）。
- **下一步触发条件**：跑一个**取证型**大任务（体量在取证、不在模块数）。若仍无可测改善、且倍数不继续下降，则本文「继续演进」的前提失效，应改判。
### 改进项分级

**本文拥有「是否做、优先级、触发条件」；机制实现细节归 `docs/dsh-v0.1.6-ptc-impact.md` §4。**

| 项 | 类型 | 价值 | 成本 |
|---|---|---|---|
| A. read-only seed + 翻转结果进数据面 | 稳健 | 失败可见、失败后果降级；0.1.6 直接给的原语 | 低 |
| B. 每角色 token / cost 归因 | 稳健 · **最对齐主线目标** | 把 ② 从「猜的档位」变成「测出的策略」；ADR 0001 已识别为上游真缺口 | 中 |
| C. 单场合规失败的可观测化 | 稳健 | 0/2 那场证明旗舰机制会静默死 | 低 |
| D. 装前契约门禁脚本 | 稳健 | 上游 issues 已关闭 + 禁改框架 + 禁 import ⇒ 漂移只能自兜 | 低 |

| F. 并发上限（guard） | 条件押注 | ADR 0001 另一个真缺口，上游仍无 cap | 中 |

**A / C / D / E 在三种结果下都不白做** —— 这是把窗口设成 2–4 周而不是「先想清楚再动」的理由。

### 明确不做（反路线图，防发散）

- 不再增加角色（5 个已够；每加一个要动 3 处 + 重训 persona，见 `pitfalls.md` #12）
- 不自建 client 面板（ADR 0001 已否决）
- 不为 explorer / librarian 加工具（无失败记录不动）
- 不做 sandbox-strip（已结案）
- 不在 alpha 上迁移（等 `0.1.6-rc.*`）

### 待决（本轮不做，但要登记）

1. **自设约束重新定价**：`AGENTS.md` 规则 3「插件零 import」的后果是**手工复刻框架深度公式**
   （连带 `pitfalls.md` #10 的四层判据 + 人工「keep in sync」纪律）。按本项目规则演进原则
   （「解决过实际失败吗」），**该约束未见失败记录**。若用 `createRequire` 取宿主的**值导出**
   （如 `delegationDepthOf`）能一次性删掉整个漂移面，则应重新定价。**本轮不改，仅登记。**
2. **两个编排面的收敛**：`ptc-roles` 用「模型写 `run_code` 组合角色调用」（已刻意关掉 `tool-workflow`
   以避免第二编排面 —— 该决策正确）；`dsh-deep-research` 用 `workflowEngine`。0.1.6 中 `workflow-ptc`
   与 PTC **共享同一沙箱实现**。角色的未来形态是「preset 角色工具」还是「workflow 原语」，需择一收敛。
3. **全 PTC 角色重估**：read-only 策略让「全 PTC」在机制上重新可行（可省掉翻转插件）；但
   **读范围不受限、且可起进程/联网** ⇒ 需先回答「只读角色是否要求读范围受限」。若是，则 native + allow-list
   仍是唯一手段，翻转必须保留。
   **归属（2026-09-16 记）**：机制侧的方案 A/B 评估归 `docs/dsh-v0.1.6-ptc-impact.md` §4.2；本文只保留
   「做不做 / 何时做」。

4. **任务工作区协议（窗口前置，2026-09-20 登记）**：对照实验要求「同一任务」，而两场真实任务的工作区
   **都不是 git 仓库**（`git rev-parse` 报 fatal）—— 没有基线提交、没有回滚点，子代理越界写入只能靠人肉确认，
   臂之间也无法隔离重放。⇒ 窗口开始前定死：每个任务工作区先 `git init`、把**冻结规格**作为首个提交；
   各臂用独立 clone / worktree。**证据**：2026-09-19 两场真实任务的目录状态，以及一次尝试做对照时正是被这个前提卡住。
   - **2026-09-20 两臂对照补两条**：① **差异验收必须连退出码一起比** —— 只比 stdout 会漏掉取反规则那类分歧
     （`keep.log`：git 打印取反规则**且返回 0**，而按原契约实现的工具返回 1）；② **交付物收尾必须提交** —— 两臂都只留了冻结提交、
     实现全躺在工作树里 ⇒ 没有版本锚，既不能回滚也无法二次复现。
   - 第三条（可比性）：**冻结规格不是只读的** —— 臂一的编排器在运行中改了自己的 `CONTRACT.md`（+5/−1；按所有权表它拥有该文件，
     合规），代价是两臂的契约文本不再字面相同。要严格可比，应显式规定「编排器可修订，但每次修订都落一条 commit」。
5. **中止子代理的判据（条件押注，2026-09-20 登记）**：`session-aef6f35a` 中途停掉 3 个 `implementer`
   （各已耗 6.3M / 16.5M / 6.7M raw token）。停止本身可能是对的，但**没有成文判据** ⇒ 事后分不清停早了还是停晚了。
   ⇒ **触发条件**：再出现一次「停得太早 / 太晚」且**有具体损失可指**的实例，再定判据并写进 orchestrator persona；
   在此之前只在本文登记。
6. **薄版本 `ptc-gate` 的构成（2026-09-21 定案、实施完成）** —— 与 `ptc-roles` 并列的第二个 preset；构成如下（Q1–Q14 由 `grill-me` 逐条定案）：
   - **保留**：① **意图门**（`intent-gate-watchdog.mjs` 及六桶判据 —— 唯一被实测证明有用的机制：3 次真实拒绝 + 模型补行重发）；
     ② orchestrator persona 的**过程部分**（Phase 0 授权边界 · Communication 含交班行 · Failure recovery · Verification · Hard blocks，约 100 行）；
     ③ **一份通用委派能力**：一个 `dsh-tool-subagent` 实例（`provider: spawn` / `backgroundMode: continuable` / `maxDepth: 1`）—— 这就是「按角色模型档」的落点：**档位保留、角色不保留**；
     ④ 唯一 reader 与部署/对账脚本。
